## 2. 设计压测

### 2.1 `_passes_audit` 是否改变既有行为边界？

**当前行为**：`final_score >= score_pass → pass`（不检查 critical）
**Proposed 行为**：`final_score >= score_pass AND 无 critical → pass`

**行为变更分析**：
- `score < score_pass`：不受影响（本来就不 pass）
- `score >= score_pass AND 无 critical`：不受影响（本来 pass，现在仍 pass）
- `score >= score_pass AND 有 critical`：**行为变更**（本来 pass，现在 fail → regenerate）

这正是 plan 的设计意图。变更边界清晰，无意外副作用。

### 2.2 critical 直接走 REGENERATE 是否与既有 [50,80) 分支重复或冲突？

**当前 [50,80) 分支**（audit_pipeline.py:1796-1809）：
- `score >= SCORE_PATCH AND has_critical → "regenerate"`
- `score >= SCORE_PATCH AND 无 critical → "repair"`

**Proposed 高分分支**：
- `score >= SCORE_PASS AND has_critical → "regenerate"`（新增）
- `score >= SCORE_PASS AND 无 critical → "skip"`（保持）

**分析**：不重复。[50,80) 区间的 critical → regenerate 逻辑保持不变；新增的是 [80,∞) 区间的 critical → regenerate。两个区间各自独立，共享「critical 只能 regenerate」语义。

### 2.3 三处装配点接入是否覆盖模板模式与 annual 两条路径？

**三处接入点**：
1. `generate_snapshot_report`（extraction.py:2834 之后）— 快照模板模式
2. `generate_report` LLM 路径（extraction.py:2654 之后）— 年报 LLM 模式
3. `_generate_chapters` 模板路径（extraction.py:3710 之后）— 年报模板模式

**覆盖分析**：
- 快照模板模式：✓（接入点 1）
- 快照 LLM 模式：✓（接入点 1，在 chapter 组装后、FundReport 构造前）
- 年报 LLM 模式：✓（接入点 2）
- 年报模板模式：✓（接入点 3）

**注意**：快照 LLM 模式和快照模板模式共享同一段 chapter 组装代码（行 2821-2834），所以接入点 1 同时覆盖两者。正确。

### 2.4 复用 schema_drift 语义是否准确？

`FailureCode.SCHEMA_DRIFT` 在 extraction.py 中用于：
- 抽取配置异常（disclosure locator registry 配置异常）
- 契约违反（multi-year requested_years 不符合契约）
- 字段名/重复异常（annual performance 字段名不符合契约）

装配审计失败（章节集合/顺序/标题与模板 manifest 不一致）属于「结构/契约与模板不一致」，与现有 schema_drift 语义一致。**语义准确**。

### 2.5 `_generate_and_audit_chapter` 中 critical → REGENERATE 的实现路径

Plan 提出「critical 存在 → 不通过，跳过 PATCH 直接走 REGENERATE」。

当前代码流程（audit_pipeline.py:2539-2570）：
```
2539: if final_score >= score_pass:
2540:     state.status = "passed_with_degradation" if not data_sufficient else "passed"
2543:     return content
2546: if final_score >= SCORE_PATCH:
2547:     if state.can_patch():
2548:         state.patch_attempts += 1
2549:         repairer = ChapterRepairer(...)
2554:         plan = repairer.generate_repair_plan()
2557:         if plan.strategy == "patch":
2558:             content = repairer.apply_patch(plan)
2563:         else:
2564:             # PATCH 失败，尝试 REGENERATE
2565:             if state.can_regenerate():
2566:                 state.regenerate_attempts += 1
2567:                 content = self._regenerate_chapter(...)
```

Proposed 变更：在 2539 之前插入 critical 检查：
```python
if final_score >= score_pass and has_critical:
    # 跳过 PATCH，直接 REGENERATE
    if state.can_regenerate():
        state.regenerate_attempts += 1
        content = self._regenerate_chapter(...)
        # 继续循环重新审计
    else:
        # 耗尽，模板降级
        state.status = "passed_with_degradation"
        return content
```

**分析**：逻辑清晰，与既有 [50,80) 区间的 critical 处理语义一致。REGENERATE 耗尽后降级为 `passed_with_degradation`，不会死循环。
