## P0：D4 退出码语义与 `_run_import_command` 现状矛盾

**计划声明** (D3/D4)：
> 退出码：全部成功（含全部 cached）→ 0；任一条目失败 → 2。

**代码实际** (`cli/main.py:782-784`)：
```python
if imported == 0 and failed > 0:
    return CLASSIFIED_FAILURE_EXIT_CODE  # 2
return SUCCESS_EXIT_CODE  # 0
```

import 命令的退出码语义是"**全部失败**才返回 2，部分失败返回 0"。计划提出的"**任一**失败 → 2"比现有契约更严格。

**风险**：
- 若 download 批量采用"任一失败 → 2"，与 import 的"全失败才 2"形成同项目内两套语义，破坏一致性。
- CI 脚本或用户 shell 依赖 `if [ $? -eq 2 ]` 做全量失败判断时，download 批量会误报。

**最小修复**：D4 退出码改为与 import 一致——全部条目失败 → 2，部分失败 → 0；或明确声明 download 批量有意采用更严格语义并给出理由。

## P1：`--quarters` 命名与现有 `--quarter` 不一致

**计划声明** (D1)：新增 `--quarters`（复数）。

**代码实际**：`--quarter`（单数）已用于 `download`（line 189）、`import`（line 175）、`snapshot-quarterly`（line 229），均为 `choices=[1,2,3,4]`，单值。

**风险**：用户心智模型中 `--quarter` = 单值、`--quarters` = 多值，语义可区分。但同一 CLI 中 `--quarter` 和 `--quarters` 共存易混淆（尤其 `download --quarter 1` vs `download --quarters 1,2`）。

**最小修复**：在 plan 中明确说明命名决策理由（复数表示多值集合），或改用 `--quarter` 复用现有参数名并扩展为接受逗号列表（如 `1,2,3`）——需评估 argparse `choices` 兼容性。

## P1：D3 输出格式——单 `--year` 增加 `report_type` 字段破坏"向后兼容"声明

**计划声明** (D3)：
> 仅 `--year`（无 `--year-range`）→ 保持现有单对象 JSON 输出（向后兼容 README/既有调用）。

但同一段又说批量输出包含 `report_type` 字段。问题是：单 `--year` 模式下是否也加 `report_type`？

**现状** (`cli/main.py:888-895`)：输出 dict 无 `report_type`、无 `quarter`。

**风险**：
- 若单 `--year` 不加 `report_type`，批量加 → 同一命令两种 schema，下游解析器需分支。
- 若单 `--year` 也加 → "向后兼容"声明不成立（新增字段改变 JSON 结构）。
- 现有测试（`test_cli.py` 中 download 用例）可能 assert 精确 JSON 结构。

**最小修复**：D3 明确——单 `--year` 输出是否新增 `report_type`/`quarter` 字段；若新增，删除"向后兼容"声明并说明新增字段是 additive（不影响现有字段）。

## P1：`--year-range` 在 download parser 上的默认值未明确

**现状**：import parser 的 `--year-range` 有默认值 `"2022-2024"`（`cli/main.py:172`）。

**计划声明** (D1)：`--year` 与 `--year-range` 互斥，两者都不给 → `schema_drift`。

**风险**：若 download 的 `--year-range` 沿用 import 的默认值 `"2022-2024"`，则"两者都不给"的 `schema_drift` 分支永远不会触发（`--year-range` 总有值）。需明确 download parser 上 `--year-range` 是否有默认值。

**最小修复**：D1 明确 `download --year-range` **无默认值**（`default=None`），与 import 的有默认值区分。

---

## P2：D2 `--import` 失败分类——下载失败条目"不导入"的语义边界

**计划声明** (D2)：
> 下载失败条目不导入；导入失败计入汇总（不改变下载成功状态）。

**风险**：`DownloadResult.status == "error"` 时 `file_path` 为 `None`。若 batch 编排遍历结果时未过滤 `status="error"` 的条目，直接取 `file_path` 构造 `ImportLocalReportRequest` 会传入 `None` → `ImportLocalReportRequest(pdf_path=None, ...)` 类型错误。

**最小修复**：D2 补充一句——批量编排仅对 `status ∈ {downloaded, cached}` 且 `file_path is not None` 的条目调用 import。

---

## P2：测试计划缺少 `_run_import_command` 退出码回归

**计划声明**：测试计划覆盖参数互斥/越界/失败不中断/import 汇总。

**风险**：现有 `test_cli.py` 中 import 测试覆盖了"全部失败 → 2"和"部分失败 → 0"语义。但 plan 的 D4 退出码若采用"任一失败 → 2"，与现有 import 测试的"部分失败 → 0"预期冲突——需确认 download 批量的退出码测试不会被 import 测试误导。

**最小修复**：测试计划中显式声明 download 批量退出码语义（与 import 是否一致），并添加对应测试用例。
