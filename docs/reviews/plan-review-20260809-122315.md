## Assumptions Tested

1. **锚点解析 fail-open**：plan 声称 `_resolve_anchor_table_ref` 失败返回 `None`，走候选词路径。验证：当前 `_build_contributions` 的 retrieval 分支（chat_service.py:598-606）只在 `route_plan.profile_name is not None` 时注入候选词。锚点注入在同层追加，`None` 时不注入，语义正确。

2. **aggregate 接线只影响 interactive**：plan 声称 fix/repair/regenerate 不受影响。验证：`_default_runner_factory` 不透传 handler，这三个场景的 `ChatService` 构造（main.py:1408/1573/1996）同模式。且 `ASK_SCENE_CONFIG.allowed_tools` 不含 aggregate。确认无副作用。

3. **`max_iterations` 8 可行**：plan 声称 R5 Q4 实际 8 次调用 < 12，8 是可行下界。验证：scene_config.py:103 当前为 12；ASK 为 8（scene_config.py:76）。interactive 从 12 降到 8 需要锚点收敛 + aggregate 单次成功 + 跨轮失败短路三个条件同时成立。plan 有 live e2e 验收锚，可接受。

4. **`_dedup_key` 放宽方案可实施**：plan 提议工具级归一化（search_document 去空白+CJK标点，read_section/read_table 按 ref 去重）。验证：当前 `_dedup_key` 是单一函数返回 tuple。plan 要求按 tool_name 分支返回不同 key 结构，实现上需在 `_dedup_key` 内加 if-else。plan 明确列出了每种工具的 key 结构，code-generation-ready。

5. **`failed_call_keys` 序列化兼容**：plan 声称旧 session 缺字段默认空元组。验证：session_store.py 反序列化用 `data.get("episode_summaries", [])` 模式（line 261），旧 JSON 无该字段时返回 `[]`。`failed_tool_call_keys` 同理用 `data.get(..., [])` + tuple 转换即可。需注意 JSON 中 tuple 序列化为 array，反序列化需显式转回 tuple-of-tuples。

## Findings

### 001-未修复-中-`_resolve_anchor_table_ref` 缺 `document_id is None` 显式守卫

- **位置**: §3.1 P0-1 规格，`_resolve_anchor_table_ref(document_id, contract, tool_service) -> str | None`
- **问题类型**: 契约缺失
- **当前写法**: "解析失败 / 工具不可用 / 无候选表 → 返回 None"，未提及 `document_id` 为 None 的场景
- **反例/失败场景**: interactive 首轮 `document_id` 可能为 None（用户未选年份/文档）。`_build_contributions` 接收 `document_id: str | None`，回退 `session.pinned_state.active_document_id`。若两者均为 None，`_resolve_anchor_table_ref` 调用 `search_document(document_id=None, ...)` 会抛异常或返回意外结果。
- **为什么有问题**: fail-open 语义依赖"解析失败返回 None"，但 None document_id 不是"解析失败"而是"前置条件不满足"。实现 agent 可能不加守卫直接传 None 给 tool_service。
- **直接证据**: chat_service.py:547 `document_id: str | None = None`；chat_service.py:570 `active_document_id = document_id or ps.active_document_id`；plan §3.1 "解析失败 / 工具不可用 / 无候选表 → 返回 None"
- **影响**: 实现 agent 可能生成不处理 None document_id 的代码，运行时抛异常而非优雅降级
- **建议改法和验证点**: plan 显式补充"document_id 为 None 时立即返回 None"；stop condition 增加"document_id=None 时锚点解析返回 None 且不抛异常"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 002-未修复-中-`failed_call_keys` 的 `document_id` 作用域未明确

- **位置**: §3.2 P0-2 规格，`failed_call_keys` 短路设计
- **问题类型**: 状态机漏洞
- **当前写法**: "key 含 document_id/工具级参数维度，会话生命周期内有效；上限 50 条防膨胀"
- **反例/失败场景**: interactive 模式下用户可切换年份/文档（pinned_state.active_document_id 变化）。若 Q1 在 2025 年报 aggregate 失败，key 含 2025 的 document_id；用户切换到 2024 年报再问同类问题，新 key 含 2024 的 document_id，不会被短路。这是正确行为。但 plan 未显式说明 document_id 变化时 key 自然隔离，实现 agent 可能过度去重（忽略 document_id 维度）或不去重（把所有失败 key 混在一起）。
- **为什么有问题**: `_dedup_key` 包含 `call.document_id`（llm_tool_loop.py:1606），所以不同 document_id 的调用天然不同 key。但 plan 没有显式说明这一点，实现 agent 可能在合并 `session.failed_tool_call_keys` 时忽略 document_id 维度。
- **直接证据**: llm_tool_loop.py:1605-1606 `return (str(call.tool_name), call.document_id, ...)`；plan §3.2 "key 含 document_id/工具级参数维度"
- **影响**: 实现 agent 可能错误实现 failed key 合并逻辑
- **建议改法和验证点**: plan 显式说明"failed_call_keys 的 tuple 结构与 `_dedup_key` 返回值一致，天然含 document_id 维度"；stop condition 增加"不同 document_id 的同参数调用不互相短路"
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 003-未修复-低-`_format_episode_summaries` 单条超限未定义行为

- **位置**: §3.3 P1 规格，`_format_episode_summaries`
- **问题类型**: 契约缺失
- **当前写法**: "最近 ≤3 条 EpisodeSummary，每条 ≤ title / goal / confirmed_facts（≤5 条）/ open_questions（≤3 条），总长 ≤500 token（复用 _estimate_token_count，超限丢最旧）"
- **反例/失败场景**: 单条 EpisodeSummary 的 confirmed_facts 中某一条极长（>500 token），导致即使只有 1 条也超限。"超限丢最旧"无法解决（只剩 1 条）。
- **为什么有问题**: plan 定义了 per-field 限制（≤5 条 facts，≤3 条 questions）但未定义单条 fact/question 的长度上限。极端情况下单条 fact 可能包含整段原文。
- **直接证据**: chat_service.py:431-434 `confirmed_facts=tuple(str(f) for f in ep_data.get("confirmed_facts", []))`——无长度截断
- **影响**: memory slot 注入超长文本，挤压其他 context slot 预算（Phase 8 才治理）
- **建议改法和验证点**: plan 补充"单条 fact/question 超 100 token 时截断并加 `...`"；或标注为 Phase 8 scope（当前不处理）
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open Questions

1. **`_dedup_key` 放宽后是否需要版本号？** 当前 session 中无 dedup key 版本信息。若未来再次放宽 key 结构，旧 session 的 `failed_tool_call_keys` 与新 `_dedup_key` 返回值不匹配，短路失效（静默不生效，不会报错）。plan 未提及 key 结构版本化。建议：当前不需要（首次引入），但值得在 backlog 记录。

2. **`_resolve_anchor_table_ref` 的 I/O 开销**：每次 `_build_contributions` 调用时若 profile 命中，会触发 `search_document` + `list_tables` + `read_table`（最多 3 次 I/O）。这发生在 LLM 循环之外，增加首轮延迟。plan 未讨论缓存策略。建议：当前可接受（单次 pre-computation），若成为瓶颈再加缓存。
