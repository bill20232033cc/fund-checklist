## Findings

### 1-NEEDS_FIX-高-critical-path 声明不一致

- **位置**: TL;DR 节 vs Execution Strategy 节
- **问题类型**: 不可直接实施
- **当前写法**:
  - TL;DR: `Critical Path: Task 1 → Task 5 → Task 6 → Task 9`
  - Execution Strategy (line 134): `Critical Path: Task 1 → Task 5 → Task 10`
- **反例/失败场景**: Implementation agent 不知道该优先完成 Task 9 (compaction) 还是 Task 10 (smoke test)，两处说法指向不同 task。
- **为什么有问题**: Task 9 (compaction) 不 block 任何其他 task（Blocks: None），不应在 critical path 上。Task 10 (smoke test) blocks F1-F4 final verification，理应在 critical path。TL;DR 的声明是错误的。
- **直接证据**: Plan 第 18 行 vs 第 134 行，两处 critical path 不同。Task 9 的 Parallelization 节（line 724）写 `Blocks: None`，与其在 critical path 上的定位矛盾。
- **影响**: 实施 Agent 跑偏 — 可能优先实现 compaction 而非 smoke test，导致 Wave 3 被延迟
- **建议改法和验证点**:
  - TL;DR line 18: 将 `Task 9` 改为 `Task 10`
  - 验证：`grep "Critical Path" .sisyphus/plans/phase7.2-implementation.md` 只有一处声明
- **修复风险**: 低
- **严重程度**: 高

### 2-NEEDS_FIX-中-fix-CLI-子命令缺少独立-task

- **位置**: Task 4 (line 349-425)、DoD (line 66)
- **问题类型**: 范围漂移 / 不可直接实施
- **当前写法**:
  - DoD (line 66): `fix --chapter 3` 检测并补强占位符
  - Task 4 (line 365): `CLI 接入：通过 repair --mode fix 或独立 fix 子命令触发`
  - Task 5 (repair CLI) 不提 `--mode fix`
  - Task 6 (regenerate CLI) 不涉及 fix
- **反例/失败场景**: Task 4 只建 SceneConfig + prompt + `_fix_chapter_placeholders()`，但没有 CLI 子命令 task。Task 5/6 的 agent 不知道该不该在自己的 task 里接 fix CLI。最终 DoD `fix --chapter 3` 无人实现。
- **为什么有问题**: DoD 要求 `fix --chapter 3` 可用，但没有 task 负责 CLI parser + subcommand 注册。Task 4 虽然提及 CLI 接入但用"或"连接两种不同方案，未做裁决。
- **直接证据**:
  - Plan line 66: DoD 包含 `fix --chapter 3`
  - Plan line 365: Task 4 说 "CLI 接入：通过 `repair --mode fix` 或独立 `fix` 子命令触发"
  - Task 5 What to do (line 429-443) 没有 `--mode fix`
  - Task 6 What to do (line 486-511) 不涉及 fix
- **影响**: 实施 Agent 跑偏 — fix 功能的 CLI 入口无人实现，DoD 第 4 项无法验收
- **建议改法和验证点**:
  - 选项 A: 在 Task 5 的 What to do 中明确增加 `--mode fix` 参数和 `_fix_chapter_placeholders()` 调用
  - 选项 B: 新增独立 Task 4b（fix CLI 子命令），在 Wave 2 并行
  - 选项 C: Task 4 改为包含完整 CLI 接入（不仅是 `_fix_chapter_placeholders()` 函数，也包括 subparser 注册）
  - 裁决后更新 DoD 和 Task 4/5/6 的描述以消除歧义
- **修复风险**: 低
- **严重程度**: 中

### 3-NEEDS_FIX-中-task-依赖声明多处不一致

- **位置**: 各 Task 的 Parallelization 节
- **问题类型**: 不可直接实施
- **当前写法**:

- **为什么有问题**: 依赖声明与实际功能耦合不匹配。Task 8 (多轮对话) 依赖 Task 1 (删除预取)，不依赖 Task 6 (regenerate CLI)。
- **直接证据**:

  - Plan line 580: Task 7 blocks Task 8
  - Plan line 239: Task 2 blocks Task 4
- **影响**: 实施 Agent 跑偏 — Wave 2 并行效率降低，Task 8 被不必要地串行化
- **建议改法和验证点**:
  - Task 6: `Blocks: Task 10` (smoke test)
  - Task 7: `Blocks: Task 10` (smoke test)
  - Task 2: `Blocks: Tasks 5, 6` (removing Task 4)
  - 验证：画依赖图确认无循环且关键路径正确
- **修复风险**: 低
- **严重程度**: 中

### 7-NEEDS_FIX-低-wave2-并行同文件编辑冲突风险

- **位置**: Task 5 + Task 6 (both modify `fund_agent/cli/main.py`)
- **问题类型**: 切片过粗 / 不可直接实施
- **当前写法**: Task 5 和 Task 6 都在 Wave 2 并行执行，都在 `main.py` 中新增函数和 subparser 注册。
- **反例/失败场景**: 两个 deep agent 在独立 worktree 中各自修改 `main.py`，merge 时产生冲突。subparser 注册在同一函数 (`_setup_parsers` 或类似位置)，新增的 `_run_repair_command` 和 `_run_regenerate_command` 函数可能插入到相同位置。
- **为什么有问题**: 计划说 "YES (different function in same file as T6)" 但 subparser 注册需要改同一段代码（argparse subparsers 区），不是不同 function 就能避免冲突的。
- **直接证据**: Plan lines 449-450: `Can Run In Parallel: YES (different function in same file as T6)` — 但两 task 都需要在 `_setup_parsers()` 和 `main()` dispatch 中注册 subparser 和 handler，这些改动冲突概率高。
- **影响**: 后续返工 — merge 冲突需要人工解决或重新编排
- **建议改法和验证点**:
  - 选项 A: Task 5 和 Task 6 串行化（同一个 agent 按顺序做 repair → regenerate）
  - 选项 B: Task 5 先做，Task 6 基于 Task 5 的 commit 做（半串行）
  - 选项 C: 保持并行但在 plan 中标注 merge 策略（谁先合谁负责解决另一个的冲突）
- **修复风险**: 低
- **严重程度**: 低
